# ReplicaHub — envío real, Dashboard y trazabilidad de transmisiones

## Qué se corrigió

1. **Envíos reales exclusivamente.** `service-push-replicas` ya no comprueba ni ejecuta `DRY_RUN`; incluso si el `.env` antiguo mantiene `DRY_RUN=true`, el worker realizará llamadas HTTP reales. No expone una opción para simular desde el panel. **Antes de activar PM2 verificar `SUTRAN_ENDPOINT_URL`, token y unidades asignadas**: la actualización hará envíos reales.
2. **Respuesta verificable.** Un HTTP 2xx únicamente se cuenta como éxito si el cuerpo de la API no indica un rechazo conocido. HTTP 403/401 queda como `FAILED`, HTTP 503/429 como `RETRY` hasta agotar intentos y falta de respuesta HTTP como error de red/timeout. No se inventa ninguna respuesta si no se recibe una.
3. **Historial durable de intentos.** Nueva tabla `transmission_attempts`; por intento registra hora, estado, HTTP, duración, payload, cuerpo de respuesta y error. Mantiene los intentos de antes de un reprocesamiento manual (`cycleAttempts` permite un nuevo ciclo sin sobrescribir historial). **No incluye tokens ni cabeceras de autenticación.** El histórico antiguo conserva su estado y respuesta final pero no tiene desglose retroactivo por intento.
4. **Dashboard de PostgreSQL.** Solo muestra recibidas, enviadas y fallidas/reintentando. Las recibidas se cuentan en `raw_messages`; el estado de repetidor y sus unidades salen de asignaciones y envíos reales. Ante fallas de consulta, muestra un error en vez de ceros inventados.
5. **Transmisiones.** Filtros: cliente, repetidor, placa/IMEI, estado, fecha desde/hasta y tipo de fecha (registro, evento GPS, recepción, último intento). Intervalos inclusivos por día en hora **America/Lima**. Tabla con último intento y confirmación HTTP. El detalle muestra respuesta exacta del destino y cada intento. Paginación de 100 registros.
6. **Exportación.** CSV/Excel utilizan los mismos filtros de fechas y estado, incluyendo hora del último intento, HTTP, respuesta y error. Máximo 50 000 filas por descarga: subdividir intervalo si supera el límite. La ruta `/api/transmissions/export` está registrada ANTES de `/:id`.
7. **Seguridad de datos.** Se conservan las filas históricas `SIMULATED` para auditoría y reprocesamiento explícito; no se generan nuevas. No se borran tramas ni se alteran claves guardadas.

## Despliegue recomendado — VPS actual `/root/replicahub`

1. Desde Windows incorporar solo los archivos corregidos al repo local y subir `main`. Revisar `git diff --check`, probar compilación antes de `git push`.
2. En el VPS, comprobar `git status --short`; hay una modificación local anterior en `frontend/package-lock.json` que **no debe perderse**. Revisar y conservar esa corrección del lockfile; no ejecutar `git reset --hard` ni `git stash pop` a ciegas. Hacer `git pull --ff-only origin main` solo cuando Git lo permita sin sobrescribir cambios.
3. Guardar un backup de la base de datos (NO se exige duplicar el proyecto): `sudo -u postgres pg_dump -Fc replicahub > /root/replicahub-postgres-antes-de-migracion.dump`. Verificar el tamaño del archivo y disponer de espacio suficiente. Conservar los `.env` actuales fuera de Git; **no enviar credenciales**.
4. Antes de migrar: `cd /root/replicahub/backend && npm run typeorm -- migration:show -d src/config/database.ts`. Si migraciones anteriores aparecen sin aplicar o parcialmente aplicadas, revisar primero; varias migraciones viejas detienen la ejecución ante columnas previamente existentes. **No ejecutar migración a ciegas**.
5. En ventana controlada y una vez inspeccionado el estado: detener solo el worker `pm2 stop service-push-replicas`. Ejecutar `cd /root/replicahub/backend && npm run migration:run`. Deben aplicarse tanto la migración anterior `ReliableTransmissionQueue1791488000000` (si no se había aplicado) como la nueva `TransmissionAttempts1791488500000`. Si falla, revisar el log y no iniciar todavía el worker actualizado.
6. Compilar EN ESTE ORDEN (sin crear otras copias):

```bash
cd /root/replicahub/services/repeaters && npm ci && npm run build && node --test tests-sutran.js
cd /root/replicahub/backend && npm ci && npx tsc -p tsconfig.json && node --test tests-monitor-filters.js
cd /root/replicahub/services/push-replicas && npm ci && npm run build && node --test tests-worker.js
cd /root/replicahub/services/wialon-push && npm ci && npm run build
cd /root/replicahub/frontend && npm ci && npm run build
```

Si el frontend sigue con lockfile antiguo, ejecutar `npm install --package-lock-only` para sincronizarlo **y subir la corrección del package-lock.json a GitHub**, luego volver a `npm ci && npm run build`.

7. Antes de reiniciar, comprobar `.env` del backend y del worker (misma `REPEATER_ENCRYPTION_KEY` y `SUTRAN_ENDPOINT_URL` correcta), conexiones a PostgreSQL y asociaciones unidad/repetidor. Si existe `.env` con `DRY_RUN=true`, **no protege de envíos reales** en esta versión; puede retirarse por claridad.
8. Tras verificar migraciones y compilación, reiniciar de forma controlada `pm2 restart replicahub-backend --update-env`, `pm2 restart replicahub-frontend --update-env` y **por último** `pm2 restart service-push-replicas --update-env`; revisar `pm2 logs service-push-replicas --lines 100 --nostream`. El receptor Wialon solo necesita reinicio si tiene nuevos cambios; la presente actualización no cambia ese receptor.
9. Comprobar `GET /api/health` (requiere que API esté en línea) y, desde el navegador autenticado, `/api/stats/dashboard`, `/api/transmissions?limit=10` y `/api/transmissions/{uuid}`. Un `503` con `SCHEMA_OUTDATED` indica que faltan migraciones. Un fallo CORS o 401 requiere revisar origen permitido/cookies. Validar primero con **una unidad asignada**.

## Notas operativas

- `received` son mensajes RAW; `sent` son transmisiones por unidad y repetidor (una trama puede enviarse a varios destinos).
- Si la IP aún no está en whitelist, la API podría responder 403/401; también puede responder 5xx, cerrar la conexión o agotar timeout. El sistema guardará el resultado realmente observado, sin asumir de antemano un 403.
- Los `PENDING`, `PROCESSING`, `RETRY` y `SKIPPED` permanecen como estados técnicos en el módulo Transmisiones; no son contadores principales del Dashboard.
- Por ahora se implementa el adaptador **SUTRAN**. Otros destinos requieren adaptadores específicos.
